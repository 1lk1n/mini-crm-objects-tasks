# Мини-CRM «Объекты и задачи»

[![CI](https://github.com/1lk1n/mini-crm-objects-tasks/actions/workflows/ci.yml/badge.svg)](https://github.com/1lk1n/mini-crm-objects-tasks/actions/workflows/ci.yml)

**Демо:** https://mini-crm-objects-tasks-navy.vercel.app (доступы: постановщик и два исполнителя, переданы в сообщении на hh.ru)

Небольшая CRM для строительной компании: постановщик ведёт объекты (стройки) и ставит по ним задачи, исполнители берут задачи в работу и отдают на проверку. У каждой задачи есть цикл статусов и неизменяемая история.

**Стек:** React 19 + TypeScript + Vite, Supabase (Postgres, Auth, RLS), Mantine UI, TanStack Query.

- Объяснение для руководителя: [docs/for-manager.md](docs/for-manager.md)
- Решения и допущения: [docs/decisions.md](docs/decisions.md)
- Вся серверная логика и права доступа в одном файле: [supabase/migrations/20261105120000_init.sql](supabase/migrations/20261105120000_init.sql)

## Как устроена защита

Все правила доступа работают **в базе данных**: интерфейс только прячет недоступные кнопки. Если обратиться к Supabase API напрямую с ключом из браузера, получится ровно то же самое.

| Требование ТЗ | Как сделано |
|---|---|
| 1. Права закрыты на уровне БД (RLS) | RLS включён на всех таблицах. У роли `anon` (без входа) нет прав ни на что. Записывать можно только разрешённые колонки (`GRANT INSERT/UPDATE (колонки)`): `status`, `author_id`, даты и `deleted_at` через API не записываются вообще. |
| 2. Исполнитель не видит и не меняет чужие задачи | Политика `tasks`: постановщик видит всё, исполнитель видит только `assignee_id = auth.uid()`. Объекты видны только те, где у исполнителя есть задачи; история только по видимым задачам. Политик на UPDATE для исполнителя нет совсем. |
| 3. Переходы статусов проверяет база | Колонку `status` нельзя изменить через API. Сменить статус можно только функцией `change_task_status()`. Она блокирует строку (`FOR UPDATE`), сверяет переход с таблицей `task_status_transitions`, проверяет роль и что исполнитель назначен именно на эту задачу, требует комментарий при возврате на доработку и сама пишет историю. |
| 4. Историю нельзя подделать, изменить или удалить | У клиентов нет прав INSERT/UPDATE/DELETE на `task_status_history`. Кто, когда и из какого статуса, записывает сервер (`auth.uid()`, `now()`, текущий статус под блокировкой). Триггер запрещает UPDATE/DELETE истории даже ключу `service_role`. Задачи и объекты удаляются «мягко», поэтому история удалённой задачи тоже остаётся. |
| 5. Открытая регистрация отключена | `enable_signup = false` (локально в `supabase/config.toml`, в облаке это настройка проекта, см. ниже). Пользователей создаёт администратор. Роль берётся из `app_metadata`, а его может задать только администратор. `user_metadata` пользователь может менять сам, поэтому роль оттуда не читается. |
| 6. Секретные ключи не попадают во фронтенд и в репозиторий | Фронтенд использует только публичный anon/publishable ключ. `service_role` нужен только скрипту `seed.mjs`, лежит в `.env.seed.local` (в `.gitignore`) и не имеет префикса `VITE_`, поэтому не может попасть в сборку. |

Дополнительно:

- Служебные функции (`is_manager()`, триггеры) лежат в схеме `private`, которую API не публикует.
- У всех `SECURITY DEFINER` функций задан `search_path = ''`.
- Исполнитель получает одинаковый ответ «Задача не найдена» и для чужой, и для несуществующей задачи, поэтому через RPC нельзя узнать, существует ли чужая задача.
- Исполнитель видит профили только тех, кто фигурирует в его задачах (себя, постановщиков, коллег из истории своих задач), а не весь список сотрудников.

### Это проверено тестами

- **`npm run test:db`**: 95 проверок на чистом Postgres. Скрипт применяет миграцию поверх эмуляции Supabase (роли `anon`/`authenticated`/`service_role`, `auth.uid()`) и пробует каждое запрещённое действие от имени разных ролей. Запускается в GitHub Actions на каждый push.
- **`npm run security-check`**: атака на **развёрнутый** проект через публичный API (как сделал бы злоумышленник с ключом из браузера). Скрипту нужен только публичный ключ и пароль демо-пользователей, `service_role` не нужен. Ни одно действие не должно пройти. В конце скрипт проверяет, что данные не изменились.

## Запуск

Нужны Node.js 20.6+ и проект Supabase (облачный бесплатный тариф или локальный `supabase start`).

### 1. База данных

```bash
# облачный проект
supabase link --project-ref <project-ref>
supabase db push            # применит supabase/migrations/*

# или локально (нужен Docker)
supabase start              # поднимет Supabase и применит миграции
```

В облачном проекте нужно отключить регистрацию: **Authentication → Sign In / Providers → «Allow new users to sign up» = off**.

### 2. Пользователи и демо-данные

```bash
cp .env.seed.example .env.seed.local   # URL, anon key, service_role key, SEED_PASSWORD
npm install
npm run seed
```

Скрипт создаёт постановщика и двух исполнителей, 3 объекта и 8 задач в разных статусах. Задачи проходят статусы через настоящую функцию смены статуса от имени этих пользователей, поэтому история у них настоящая.

Создать пользователя вручную можно так: **Authentication → Users → Add user** (с галочкой Auto Confirm). По умолчанию он станет исполнителем. Чтобы сделать его постановщиком, выполните в SQL Editor:

```sql
update public.profiles set role = 'manager' where id = (select id from auth.users where email = 'user@company.ru');
```

### 3. Фронтенд

```bash
cp .env.example .env.local    # VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY
npm run dev                   # http://localhost:5173
```

Деплой: любой статический хостинг. Для Vercel и Netlify правила SPA-маршрутизации уже лежат в `vercel.json` и `public/_redirects`. Переменные окружения те же, что в `.env.example`.

### 4. Проверки

```bash
npm run lint && npm run typecheck
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5432/postgres npm run test:db   # любой пустой Postgres 15+
npm run security-check        # против развёрнутого проекта
```

## Структура

```
supabase/migrations/      схема, RLS, триггеры, функции (вся серверная логика)
supabase/config.toml      локальная конфигурация (регистрация отключена)
tests/db/                 SQL-тесты безопасности + эмуляция Supabase для них
scripts/seed.mjs          демо-пользователи и данные
scripts/security-check.mjs   проверка защиты на живом API
scripts/test-db.sh        запуск SQL-тестов
src/lib/                  клиент Supabase, типы БД, запросы (TanStack Query), статусы
src/auth/                 сессия и профиль текущего пользователя
src/pages/                экраны: вход, объекты, объект, задача, мои/все задачи
src/components/           формы, кнопки действий, история
```

## Экраны

1. **Вход** по email и паролю. Регистрации нет.
2. **Объекты**: список со счётчиками задач по статусам. Исполнитель видит только объекты, где у него есть задачи.
3. **Объект**: данные и задачи объекта на канбан-доске (или списком). Постановщик может создавать задачи, редактировать и удалять объект.
4. **Задача**: данные, кнопки доступных переходов (только те, что разрешены текущему пользователю в текущем статусе) и история статусов с комментариями.
5. **Мои задачи** (исполнитель): канбан-доска своих задач.
6. **Все задачи** (постановщик, дополнительно к ТЗ): доска всех задач. В режиме списка открывается на фильтре «На проверке», то есть сразу показывает, что ждёт решения постановщика.

**Канбан-доска.** Колонки соответствуют статусам. Карточку можно перетащить или сдвинуть кнопкой на ней, но только по переходам, разрешённым текущему пользователю: при перетаскивании допустимые колонки подсвечиваются, остальные затемняются. Карточки, по которым у пользователя нет действий, не перетаскиваются. Бейдж «ваш ход» показывает, сколько задач в колонке ждут именно вас. При возврате на доработку доска запрашивает обязательный комментарий. Каждое перемещение вызывает ту же функцию `change_task_status()`, что и кнопки в карточке задачи, так что правила по-прежнему проверяет база. Переключатель «Доска / Список» сохраняет табличный вид.
