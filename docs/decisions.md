# Решения и допущения

Что я решил сам там, где ТЗ допускает разные трактовки, и что сознательно не стал делать.

## Трактовки ТЗ

1. **Удаление «мягкое».** ТЗ требует сразу двух вещей: постановщик удаляет задачи и объекты, а историю статусов удалить нельзя. Если удалять физически, вместе с задачей пропадёт и её история. Поэтому удаление ставит пометку `deleted_at`: задача или объект пропадает из интерфейса и из API, а история остаётся в базе. При удалении объекта удаляются и его задачи (интерфейс предупреждает об этом). Восстановить удалённое может администратор через SQL, в интерфейсе этого нет.
2. **Принимать и возвращать задачи может любой постановщик**, а не только автор задачи. Постановщиков может быть несколько, и проверять работу может тот, кто сейчас на объекте.
3. **Исполнитель обязателен при создании задачи** и должен иметь роль «исполнитель» (проверяется в базе). Переход «Новая → В работе» делает «назначенный исполнитель», значит задача без исполнителя застряла бы.
4. **Переназначение разрешено в любом статусе.** Новый исполнитель продолжает с текущего статуса. Прежний сразу теряет доступ к задаче и её истории.
5. **Постановщик может редактировать поля задачи в любом статусе**, включая «Принята». История фиксирует только смену статусов, как сказано в ТЗ. Правки полей не журналируются (см. «Что можно улучшить»).
6. **«Принята» — конечный статус.** В ТЗ нет переходов из него, поэтому база их не допускает.
7. **Комментарий** можно оставить при любом переходе. При возврате на доработку он обязателен: пустой или из одних пробелов база не примет. Создание задачи пишется в историю первой строкой «— → Новая» от имени автора.
8. **Что видит исполнитель:** свои задачи; объекты, где у него есть хотя бы одна задача в любом статусе; в карточке объекта только свои задачи. Из профилей коллег он видит себя, постановщиков и тех, кто есть в истории его задач (например, прежнего исполнителя). Полный список сотрудников ему не нужен, поэтому он закрыт.
9. **Роли.** У пользователя одна роль, она хранится в таблице `profiles`. При создании пользователя роль берётся из `app_metadata`: туда может писать только администратор. По умолчанию назначается роль «исполнитель», то есть минимальные права. Через API роль поменять нельзя.
10. **Правила переходов хранятся в таблице** `task_status_transitions`, это единый источник правды. Функция смены статуса в базе проверяет переходы по ней. Интерфейс читает ту же таблицу, чтобы показать нужные кнопки. Поменять процесс значит поменять одну таблицу, а не код в двух местах.
11. **Смена статуса реализована функцией (RPC), а не триггером на UPDATE.** Колонку `status` клиенту писать нельзя совсем. Так проверка, запись истории и комментарий проходят одну транзакцию с блокировкой строки: два одновременных клика не создадут два перехода.
12. **Добавлен экран «Все задачи» для постановщика**, хотя в списке экранов ТЗ его нет. Он открывается на фильтре «На проверке», то есть показывает, что ждёт решения. Без него постановщику пришлось бы обходить все объекты.
13. **Сообщения об ошибках формирует база** и пишет их по-русски. Интерфейс показывает их как есть, а при обращении к API напрямую они так же понятны.

## Что можно улучшить (не входило в объём или не успел)

- **Управление пользователями в интерфейсе.** Пока пользователей создаёт администратор в Supabase или скриптом `seed.mjs`. Для интерфейса понадобилась бы серверная функция (Edge Function), которая использует `service_role` и проверяет, что вызывающий — постановщик.
- **Журнал правок полей задачи** (кто и когда сменил название или исполнителя) и восстановление удалённого из интерфейса.
- **Обновление в реальном времени** (Supabase Realtime). Сейчас данные обновляются после действий и при возврате на вкладку.
- **Вложения** (фото выполненной работы) через Supabase Storage с теми же правилами доступа, что у задачи.
- **Уведомления** исполнителю и постановщику о смене статуса (email или Telegram).
- **Автотесты интерфейса** (Playwright). Сейчас тестами покрыты база (`npm run test:db`, 95 проверок) и живой API (`npm run security-check`). Именно там находится логика доступа.
- **Типы БД** написаны вручную в формате `supabase gen types`. В рабочем проекте их лучше генерировать в CI.
- Восстановление пароля и смену пароля пользователем не делал. Пароль сбрасывает администратор.
